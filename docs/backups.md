# Database Backups

Meridian backups support operator runs and a local Windows nightly task. The tooling creates a PostgreSQL
custom-format dump from the local Timescale Compose service and verifies it by
restoring into a disposable database inside the same service.

This is not a hosted nightly schedule, offsite retention policy, or provider secret
store integration yet.

## Create A Backup

Start the local infrastructure first:

```powershell
docker compose -f infra/docker-compose.yml up -d timescaledb
```

Then run:

```powershell
pnpm db:backup
```

The output is written under ignored `backups/`, for example:

```json
{
  "ok": true,
  "command": "backup",
  "backup": "backups/meridian-20261012T102030Z.dump",
  "bytes": 123456,
  "format": "pg_dump-custom"
}
```

To choose an explicit file:

```powershell
pnpm db:backup -- --out backups/manual-before-upgrade.dump
```

The script refuses output paths outside the repository. Do not commit backup files.
They may contain strategy, account, audit, order and fill history.

## Verify A Backup

Run verification after each backup:

```powershell
pnpm db:backup:verify -- --file backups/manual-before-upgrade.dump
```

Verification creates a temporary database named like
`meridian_restore_verify_<token>`, restores the dump with `pg_restore
--exit-on-error`, checks core tables and migration metadata, then drops the
temporary database.

Timescale's pre/post-restore hooks are run only on that disposable target, following
the [official logical-backup procedure](https://www.tigerdata.com/docs/deploy/self-hosted/backup-and-restore/logical-backup).
Cleanup failure fails verification; the source database is never a restore target.

The check proves:

- the dump can be read by `pg_restore`
- schema objects restore into a fresh database
- core Meridian tables are present
- `schema_migrations` is present and readable

The check does not prove:

- a cloud/provider backup schedule exists
- offsite retention exists
- point-in-time recovery is configured
- production secrets or TLS deployment are complete
- every restored row has been semantically reconciled with an exchange account

## Custom Compose Options

Defaults match the local stack:

```powershell
pnpm db:backup -- --compose-file infra/docker-compose.yml --service timescaledb --user meridian --database meridian
pnpm db:backup:verify -- --file backups/manual.dump --compose-file infra/docker-compose.yml --service timescaledb --user meridian --database meridian
```

The script runs `pg_dump`, `createdb`, `pg_restore`, `psql`, and `dropdb` inside
the Compose service, so the host machine does not need PostgreSQL client tools.

## Scheduled Runner

Use the scheduled runner from cron, Windows Task Scheduler, a provider job, or a
deployment platform scheduler:

```powershell
pnpm db:backup:scheduled
```

It performs the full local acceptance sequence:

1. create a timestamped backup under ignored `backups/`
2. restore that backup into a disposable database
3. check core schema and migration metadata
4. write an evidence JSON file under ignored `logs/verification/phase-5/backups/`
5. prune old local dumps, keeping the newest seven by default

Use `--keep-local` to change the local retention count:

```powershell
pnpm db:backup:scheduled -- --keep-local 14
```

Use `--manifest-out` when a scheduler expects a stable output path:

```powershell
pnpm db:backup:scheduled -- --manifest-out logs/verification/phase-5/backups/latest.json
```

The command exits nonzero if backup creation or restore verification fails. In a
real deployment, configure the scheduler/provider to alert on that nonzero exit
and ship the dump to private durable storage after the command succeeds.

## Local Windows Schedule

```powershell
pnpm db:backup:install
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/backup-task.ps1 -Action Start
pnpm db:backup:status
pnpm db:backup:check
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/backup-task.ps1 -Action Status
```

The current-user tasks run hidden with limited privileges and no stored password:

- `Meridian Nightly Database Backup`: 03:00 Dubai time, plus login catch-up; three retries spaced five minutes apart. Already verified due windows are skipped.
- `Meridian Backup Health Check`: every 30 minutes plus login. Missed backups alert after a two-hour grace period. Failed/interrupted jobs and unavailable latest archives also alert.

Installation requires Windows `Arabian Standard Time` and refuses unrelated tasks
with matching names. Neither task wakes the laptop or starts Docker. Tasks require
an interactive logged-in session; shutdown/sleep/offline delivery is not remotely
monitored. Catch-up/checks resume when the laptop is available and you log in.
Initial actual task execution passed; a future full nightly cycle is not yet proved.

Private Telegram destination comes from ignored
`infra/alertmanager/.local/alertmanager.yml`, generated by existing Telegram setup.
Do not print or commit it. Alerts are sent directly, so Docker downtime does not
disable delivery if the laptop/network remain available. Identical outages are
deduplicated; undelivered messages retry on later checks, at least five minutes
apart. Recovery waits for healthy backup state. API acceptance does not prove
human receipt; delivery plus outbox persistence is not exactly-once.

Status, bounded wrapper logs and alert outbox live under
`logs/verification/phase-5/backups/local/`. Archives remain in ignored `backups/`.
Retention prunes only `meridian-YYYYMMDDTHHMMSSZ.dump` files after a successful
restore check; manual-named archives are not deleted. Seven snapshots are not a
disk quota. Failed verification archives and manual/test dumps need operator
review; live database and NDJSON retention are separate policies.

Latest-artifact checks inspect path, size and custom-format header, not a full
integrity hash. Nightly restore verification checks readable core tables, migration
metadata and reports row counts; it does not reconcile every row to the source or
exchange. Disposable target creation/restore needs local disk and IO capacity.

Interrupted jobs leave exclusive `.run.lock` or `.notification.lock` files rather
than risking overlapping work. Before removing a stale lock: inspect its PID and
the matching task/logs, confirm no backup/restore remains active, and check for
leftover `meridian_restore_verify_*` databases. Never terminate an arbitrary PID
or drop the source database. Remove only the reviewed exact lock path, then rerun
the backup. Unwritable state storage triggers a generic best-effort monitor alert;
durable dedup is unavailable while that storage cannot be written.

Bounded real verification (reads source, restores disposable targets, sends at most
two labeled Telegram messages; creates ignored evidence/dumps):

```powershell
node scripts/verify-local-backup.cjs
node --test scripts/db-backup.test.cjs scripts/local-backup.test.cjs
```

To unregister only the owned, non-running local tasks:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/backup-task.ps1 -Action Remove
```

## Deferred Production Work

For full Phase 5 acceptance, add a provider-backed scheduled job that runs the
scheduled runner, uploads the verified dump to private durable storage, applies
remote retention, alerts on failure, and periodically restores into disposable
infrastructure. Keep the restore evidence separate from the backup artifact itself.
